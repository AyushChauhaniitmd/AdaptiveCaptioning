OPTIMIZATION NOTES — Frame Sampling Reduction
==============================================

Currently, for each subtitle entry, three frames are sampled — one near the
start, one at the midpoint, and one near the end. The worst-case score across
all three is used to decide placement. This ensures that if any part of the
subtitle window has busy content, the region is penalized.

If further time reduction becomes necessary, the plan is to use only the
starting frame of each subtitle entry. This removes the midpoint and end
samples entirely, cutting roughly two-thirds of the per-subtitle scoring cost.

The main risk is that content changes occurring mid-subtitle or toward the end
of the display window will go undetected. This matters most for physicalboard
and smartboard videos where the presenter or board content can change quickly.
For ppt and coding videos, where the screen is mostly static, the accuracy
impact is expected to be minimal.

A middle-ground option is to keep two frames — start and midpoint — which
saves about one-third of the cost while retaining some mid-subtitle awareness.

4. ASS output and JS subtitle renderer — DEFERRED
Pipeline currently outputs VTT only. An ASS (Advanced SubStation Alpha) builder
was prototyped (build_ass() with \pos, \clip, \an tags — pixel-exact in VLC/mpv/
PotPlayer/Kodi/MX Player etc.) and a JS VTT-parser renderer was built into
player.html (strict div-based region bounding, no native <track>). Both were
removed for now to keep the pipeline lean. Re-add when cross-player distribution
or pixel-exact browser rendering becomes a requirement.
